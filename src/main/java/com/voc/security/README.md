## I. Authenticate users

We **do not** store user's password in plain text, instead we hash them. We use [Bcrypt](https://bcrypt.online) to hash passwords securely.

**Why we hash the password?**

- In production, we do not want to expose the user's passwords.
- If attacker somehow get the user table data, they can't do anything about it.

**Authentication Flow:**

1. User submits username and password
2. AuthManager hashes submitted password using Bcrypt
3. Hashed password compared with stored hash in database
4. JWT + session created if credentials match

**Important:** Never store passwords in plain text

## II. Sessions and JWT Management

Handles user session tracking and secure token-based authentication. This ensures that only authorized users can access protected routes while maintaining scalable session management.

**Why Sessions and JWT?**

- [JWT](https://www.jwt.io) or [Json Web Token](https://www.jwt.io) allows stateless authentication — the server does not need to store user session data in memory for every request which will improve the server's performance.
- Session management allows token revocation and tracking of active users.
- Together, they improve security and scalability for multi-server setups.
- JWT will be use for API calls, for security reason to prevent spam call to API for an unthorized individual.

### What is session?

Session is an identifier for the user. It is a long-lived key for the user to access the website that use to get a short-lived token.

We have 2-3 types of token, a short-lived token to access the API(JWT), a token for access the webpage(Session), and a refresh token that use to refresh API(JWT) token.

- Short-lived JWT for API requests
- Long-lived session for website access
- Refresh token for renewing JWT

### How a session work?

Whenever the user logs in, we generate 3 of them at the same time. SessionID will be pair with a Refresh Token in secure cookie.

Session ID will have the compound string of `SessionID:RawRefreshToken`

Afterward we hashed refresh token using the same technique as hashing password([Bcrypt](https://bcrypt.online)) for security reason so the person who could access the database won’t be able to see it and gain access to the user's account.

JWT Token will be generated by rotating the key, the key will be used to verify the JWT token which will return us a user's ID and username. The key will be rotate everyday at midnight.

Whenever a JWT token expires, new SessionID and Refresh Token will be regenerated alongside it. This extends the session lifespan.

**Session Flow:**

1. User logs in successfully via AuthManager
2. AuthManager generates a JWT access token and a refresh token packed with SessionID
3. JWT sent to user; sessionid + refresh token stored in SessionTB (hashed for security)
4. JWT will be kept in sessionStorage and SessionID:RefreshToken will be kept as Cookie with `sameSite = strict` for [CSRF](https://owasp.org/www-community/attacks/csrf) reason
5. For each request:
   - JWT is verified by JWTManager
   - If expired, refresh token can be used to issue a new JWT
   - Session expires after configured time or manual logout

**Important:**

- Refresh tokens are hashed in the database for security
- JWT should contain only minimal, non-sensitive info (user ID, username, expiration)
- Keys are rotated daily to reduce the risk of exposure in case of a leak.
- Sessions should be invalidated on suspicious activity (IP change, token misuse) but we will skip this step for this project complexity.

**Future Improvements / Scalability:**

- Implement rate-limiting to prevent brute-force attacks
- OAuth login support
- Email verification for account registration
- Advanced logging and anomaly detection
- Though current CSRF protection we're using is basic Cookie `sameSite = strict` to reduce complexity for demonstration purpose. We can later implement more advance CSRF protection.
- While JWT supports stronger algorithms like RS256 (asymmetric encryption), we use HS256 in this project to keep implementation simpler and reduce complexity for demonstration purposes. In a production system, RS256 or key rotation strategies may be more appropriate. [See more on what's the difference](https://auth0.com/blog/rs256-vs-hs256-whats-the-difference/)

### This module ensures that user authentication and session management are secure, scalable, and maintainable for the web application.
